# 分章技术栈文档写作规范

这份规范定义「一份技术栈文档」怎么分章、怎么编号、怎么被 AI 检索、以及新内容插到哪里。
它同时是 `kirara_docs` / `kirara_docsync` 的运行时契约：插件按这些规则发现文档、选章、给插入计划；
换项目（或换一套文档）时，只要目录与标题符合本规范，插件不需要任何代码改动。

> 目标不是排版好看，而是让**下一个会话**能先用最低成本定位到一小节，并且知道「这条结论该写进哪一章的哪一节」。
> 一份 258 KB 的单文件做不到这一点：整篇读会挤爆上下文，只 grep 又会丢结构（不知道命中行属于哪个模块）。

## 1. 目录布局

一个「分章文档集」是 `docs/` 或 `app/docs/` 下的一个目录（名字不限，常见为 `技术栈文档/`）：

```text
docs/技术栈文档/
├── README.md                  # 可选：文库入口 / 阅读顺序（不是模块章）
├── _写作规范.md               # 可选：本规范副本；下划线开头 = 规范/临时文件，不参与正文检索
├── 01-总览与架构.md           # 模块章：01–89
├── 02-启动与外壳.md
├── …
├── 14-附录-清单总表.md        # 参考/附录也放在 01–89 内
├── 99-变更记录.md             # 单卷形态：只写流水，日期倒序
└── 99-变更记录/               # 多卷形态（二选一）：一个卷一个文件
    ├── 00-索引与编号映射.md   #   卷索引 / 历史章号映射
    ├── 01-M3评论闭环-….md
    └── 02-0.9.5至0.9.7-….md
```

发现规则（插件按此实现，不写死路径）：

- 在项目的 `docs/` 与 `app/docs/` 下递归最多 2 层；
- 某个目录同时含 **≥2 个 `NN-标题.md`（NN = 01–89）** ⇒ 视为一个分章集；
- `99-变更记录/` 是流水卷目录，**不算模块章**；其中的 `NN-*.md` 只作为变更记录；
- `_` 开头的文件是规范/临时文件，不参与正文检索；`README.md` 作为入口页展示，不作为模块章。

> `Kirara_Server_Studio` 目前是单卷形态（`01…14 + 99-变更记录.md`）；
> `Kirara_Media` 迁移后是「模块章 + `99-变更记录/` 多卷」形态；插件两者都支持。

## 2. 文件命名

| 名字 | 规则 | 例子 |
| --- | --- | --- |
| 模块章 | `NN-标题.md`，NN 两位数，标题用中文短名 | `03-认证与账户.md` |
| 附录 | 仍用 `NN-`，编号取 01–89 的下一号 | `14-附录-清单总表.md` |
| 单卷流水 | `99-变更记录.md` | — |
| 多卷流水 | `99-变更记录/NN-时间段.md` + `00-索引与编号映射.md` | `99-变更记录/09-1.5.0与iOS原生化-2026-11-11至11-15.md` |
| 规范/临时 | `_` 开头 | `_写作规范.md`、`_历史原文暂存-….md` |

- **编号不复用、不留空**：新增模块取当前最大模块号 +1；删模块时不要回收编号（旧链接会指错）。
- 文件名里的标题与 H1 标题保持一致；改名时全库搜索旧文件名与 `#anchor` 一起改。

## 3. frontmatter

模块章必须带 frontmatter（`99-变更记录` 豁免）：

```markdown
---
module: 认证与账户
level: 基础层
files:
  - Services/ILoginService.cs
  - Services/RemoteLoginService.cs
  - Views/Pages/LoginPage.xaml(.cs)
related: [04-数据与模型.md, 05-加密与安全.md, 99-变更记录.md]
---
```

| 字段 | 必填 | 含义 / 写法 |
| --- | --- | --- |
| `module` | 是 | 模块名，通常与章标题一致 |
| `level` | 建议 | 分层：基础层 / 核心层 / 功能层 / 展现层 / 参考 / 索引 / 流水 |
| `files` | 是 | 该章覆盖的源文件。用仓库相对路径；成对文件写 `Views/Pages/LoginPage.xaml(.cs)`；可写目录前缀 `Services/` |
| `related` | 建议 | 相关章节文件名，不要带 `#anchor`；优先写同目录 `NN-标题.md` |
| `legacy` | 可选 | 本文内容在旧单篇文档里的章号（如 `"5.1, 5.2, 12.1–12.37"`），只作检索桥梁，插件不解析 |

`files` 是**自动写文档最重要的索引**：`kirara_docsync` 先拿本次改动路径去匹配它，命中即认为「这一章是权威落点」；
匹配不到才退回标题关键词。所以新增/移动源文件时，把 `files` 一起补上，否则下一轮又会按关键词猜。

## 4. 标题、编号与锚点

### 4.1 标题层级

```markdown
# 03 认证与账户

<a id="auth"></a>
## 03.1 认证系统

### 职责与边界
```

- H1 固定为 `# NN 标题`，NN 与文件名一致；一篇文件只有一个 H1。
- H2 固定为 `## NN.M 标题`，M 在本章内从 1 连续递增；一章不要出现两个 `03.2`。
  兼容补位编号 `NN.Ma`（如 `03.4a`，用于在既有节后插一条而不重排全章）：插件识别它，
  下一节建议仍取数字部分最大值 +1（`03.5`）。
- H3 不编号，按语义起名（`职责与边界` / `关键文件` / `主流程` / `设计决策` / `陷阱与约定` / `自测点`）。
- 导语性 H2（如 `## 本篇范围`）可以放在第一个编号小节之前，不要求编号；审计不会报。
- 正文里不要写「本章」「本轮」这类相对时间；「本轮改了什么」只进 99。

### 4.2 显式锚点

跨文档链接只认**显式锚点**。Markdown 对中文标题自动生成的 anchor 不可控（不同渲染器结果不同），所以：

```markdown
<a id="account-settings"></a>
## 03.2 账号设置
```

- 锚点写在 H2 **前一行**（空一行也允许；插件会在标题前后 2 行内查找）；
- id 用小写英文 + 连字符，语义化：`auth`、`account-settings`、`user-data-context`；
- 同一**文件内** id 唯一；不同模块文件可以同名（跨文件链接带文件名，不会歧义）；
- 已有小节被链接引用却没有锚点 ⇒ 审计报「断链 / 找不到锚点」。

### 4.3 交叉链接

```markdown
[账号设置](./03-认证与账户.md#account-settings)
[令牌管理流程](./04-数据与模型.md#token-manager)
```

- 同一目录内用 `./NN-标题.md#anchor`；跨目录用相对路径；
- 不要链到 `#03.2` 这种自动锚点；
- 移动/重命名章节时，全库搜文件名与 `#old-anchor` 一起改（审计会报断链）。

## 5. 内容归属：正文 vs 变更记录

| 内容 | 写哪里 | 判断 |
| --- | --- | --- |
| 稳定的设计结论、接口契约、构建命令、约束、坑与判据 | 对应模块章的 `## NN.M` | 下一轮会照着它写代码 |
| 「本轮做了什么、为什么、当时的证据」 | `99-变更记录` 的日期/卷条目 | 流水；不进入模块正文 |
| 「修复 XXX」 | 改写模块章里描述**旧行为**的段落 + 99 留一条 | 不新开「修复 XXX」小节 |
| 一次性的调试记录、被推翻的方案 | 99 条目里写清楚「已否决 + 判据」 | 模块正文只留最终结论 |
| 依赖版本 / 构建命令 / 端口 / 端点 | 模块章的稳定事实 + 必要时 99 | 下一轮模型会直接引用 |

这条边界是长期可维护性的核心：正文越写越像提交日志，检索就会失效；反过来，流水里藏稳定结论，下一轮又会找不到。

## 6. 插入模板

### 6.1 在既有章里新增小节

适用于新功能 / 新模块能力，且该章没有描述它的既有小节。

1. 找到该章最后一个 `## NN.M`；新小节号 = M + 1。
2. 在文件末尾（或该章最后一个 H2 之后）追加：

```markdown
<a id="new-feature-slug"></a>
## 03.5 新能力名称

### 职责与边界
- 负责：……
- 不负责：……（指向相邻章节）

### 关键文件
| 文件 | 角色 |
| --- | --- |
| `Services/XxxService.cs` | …… |

### 主流程
……

### 设计决策
……

### 陷阱与约定
- ……

### 自测点
- ……
```

3. 更新 frontmatter `files:`（加上本次改到的源文件）与 `related:`（关联章节）。
4. 如果新能力引用了其他章，补交叉链接；被引用的章节要有显式锚点。
5. 在 99 变更记录补一条。

> `kirara_docsync` 的 `edit.mode='new'` 就是这条模板：它会给出 `NN.M`、建议锚点、插入行号与 frontmatter 补文件清单。

### 6.2 新增一个模块章

适用于一个足够独立的新模块（不是某一章里的小能力）。

1. 取当前最大模块号 + 1（如已有 14，则 `15`），不补空号。
2. 新建 `NN-标题.md`，带 frontmatter（`module` / `level` / `files` / `related`）。
3. H1 `# NN 标题`；第一章 `## NN.1`。
4. 在入口 `README.md` / 索引里补一行（如果该文档集有入口页）。
5. 在 `related:` 里与相邻模块互链。
6. 99 补一条；如果新增了 DI 注册 / 内置方案 / 清单项，同步附录章（如 `14-附录-清单总表.md`）。

### 6.3 单卷 99 变更记录

`99-变更记录.md` 的结构：

```markdown
# 99 变更记录

> 本文件只记录**发生了什么、什么时候**。稳定的技术结论写在对应模块文档里，此处不重复。
> 条目按日期倒序；同一天的条目缘于当时的追加顺序。

## 2026-11-16 · 文档重构：按模块拆分 + 统一编号

- ……
```

插入位置：**引言之后、最新日期条目前**（通常是第 5 行后）。新条目格式：

```markdown
## YYYY-MM-DD · 一句话标题

- **背景/根因**：……
- **改法**：……
- **判据/验证**：……
- 详见 [模块章](./03-认证与账户.md#auth)
```

- 日期用本地日期（Asia/Shanghai），不要写「今天」；
- 标题写「做了什么」，不要只写「修复 bug」；
- 正文里不重复模块章的稳定结论，只写差异、证据、被否决的方案。

### 6.4 多卷 99 变更记录

`99-变更记录/` 形态：

```text
99-变更记录/
├── 00-索引与编号映射.md      # 分卷表 + 历史章号 → 文件/锚点
├── 08-….md                   # 一卷 = 一个时间段
└── 09-….md                   # 最新卷
```

- 新条目追加到**最新卷末尾**（不要插到卷首）：`## <历史章号> · 标题`，历史章号取所有卷已有条目的最大值 + 1；
- 小节按该卷体例（常见 `### NN.1 一句话`、`### NN.2 改动清单`…）；
- 同步 `00-索引与编号映射.md`：分卷表加一行，章号表补「历史章号 → 本卷文件/锚点」；
- 新卷只在时间段切换时创建；一卷内的条目保持时间顺序。

> 多卷形态的 `00-索引` 是**强约束**：全仓注释里的「技术栈 §NN.M」靠它解析到具体文件与锚点。
> 只加卷、不改索引，等于让旧引用断掉。

### 6.5 附录 / 清单总表

新增 DI 注册、内置方案、配置项、清单条目时，除了模块章，还要同步附录章（通常是 `14-附录-清单总表.md`）：

- `## 14.1 内置方案清单`
- `## 14.2 DI 注册总表`
- `## 14.3 其它清单索引`

附录是「一次性查全」的落点；模块章讲「为什么」，附录讲「有哪些」。

## 7. 审计规则

`kirara_docs({ mode: 'map' })` 会在末尾给出结构审计。它只报会让下一轮读错/写错的问题：

| 代码 | 含义 | 修法 |
| --- | --- | --- |
| `frontmatter` | 模块章缺 frontmatter | 补 `module` / `level` / `files` / `related` |
| `h1-number` | H1 未以章号开头 | 改成 `# NN 标题` |
| `section-number` | `##` 小节未按 `NN.M` 编号 | 补编号；新小节按本章最大值 +1 |
| `duplicate-anchor` | 同一文件内锚点重复 | 改成语义唯一的 id |
| `broken-link` | 跨文档链接目标文件不存在 | 补文件或改链接 |
| `broken-anchor` | 目标文件没有该锚点 | 在目标 H2 前补 `<a id="…"></a>` |
| `broken-related` | `related` 指向不存在的文件 | 改文件名或删掉 |

单卷/多卷流水不参与「frontmatter / 小节编号」审计；但它们的跨文档链接同样会被检查。

## 8. 换项目：最小接入步骤

1. 在 `PROJECTS` 里登记项目（`key` / `dir` / `build` / `docs`），并设 `techDocs` 指向分章集目录或主文档。
2. 按本规范建立 `docs/技术栈文档/` 或 `app/docs/技术栈文档/`。
3. 给每个模块章补 frontmatter 与显式锚点；把入口/索引页（如有）放进 `README.md`。
4. 跑 `kirara_docs({ mode: 'map', project: '<key>' })`，确认章 / 节 / 锚点被正确识别；
   末尾的审计逐条清掉。
5. 跑 `kirara_docsync` 做一次真实改动，确认它选中的章与插入计划符合预期。

插件不要求目录名必须叫 `技术栈文档`，也不要求一定是单卷 99；只要求「≥2 个 `NN-标题.md`（01–89）」
与「`99-` 流水目录/文件」这两个约定。

## 9. 反例

- ❌ 把新功能写进 99：下一轮检索不到，正文也没有稳定结论。
- ❌ 把「修复 XXX」写成 `## 03.5 修复 XXX`：正文变成提交日志，且与 99 重复。
- ❌ 只改 `##` 标题不改正文里的旧结论：链接能点开，但下一轮读到的是过期事实。
- ❌ 跨文档链接用自动锚点 `#03.2`：换渲染器就断，审计也会报。
- ❌ 新模块直接占用 `99` 之外的任意空号（如 16 但 15 空着）：编号不再可预测；新增一律取最大 +1。
- ❌ 多卷 99 只加卷、不更新 `00-索引`：全仓旧引用解析不到具体文件。
